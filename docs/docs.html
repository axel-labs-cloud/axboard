axboard

A fast, self-hosted dashboard for your homelab — the front door to every service you run. One Go binary, an embedded React app, and a YAML file you own.

Overview

What it is

axboard is a drag-and-drop dashboard of widgets — most importantly clickable app cards with health pings — that sits in front of everything you self-host. It's a single binary with the SPA embedded, no database and no accounts required, LAN-bound by default.

Edit it however you like — both ways stay in sync. Build the whole board in the browser: drag & resize widgets, and add or edit services, dashboards, alerts, status pages and themes with point-and-click panels. Or hand-edit the YAML in your editor. Every change hot-reloads instantly, and the UI's structured edits are written straight back to your config.yaml.

It is deliberately not a metrics collector (health checks are liveness only — point at Grafana for real observability), not a plugin platform, and not multi-tenant. Keeping it small is the point.

Getting started

Quick start

Podman / Docker Compose

git clone <repo> axboard && cd axboard
mkdir -p config && cp config.example.yaml config/config.yaml
podman compose up -d      # or: docker compose up -d

Open http://localhost:8080. Edit config/config.yaml in your editor — the server hot-reloads on save. The bundled config.example.yaml is a full, working starter with services, groups, a top bar, and two themed dashboards.

i
The compose file runs with host networking so the Host stats, Resource gauge and Network graph widgets can read real host network I/O, and so Wake-on-LAN can reach the LAN broadcast. It also mounts a read-only container socket for auto-discovery. All of it is optional and commented as removable.

Single binary

make build      # needs Go 1.26 + Node 22
cp config.example.yaml config.yaml
./bin/axboard --config ./config.yaml --state ./state.yaml --addr :8080

Getting started

Configuration

Two files, one clear split — this is the most important design decision in the project.

FileOwnerHolds
config.yamlYou — the UI or your editorApps, groups, dashboards, widgets, the global top bar. Written by the UI's edit panels and hand-editable; hot-reloads on change.
state.yamlaxboard (machine-managed)Grid layouts, written automatically on every drag / resize. Never edit by hand.

On a YAML parse error the UI shows a banner pointing at the line and keeps serving the last-good config — it never crashes on a bad save. Themes and widget-style settings are browser-local.

A minimal config

apps:
  - id: jellyfin
    name: Jellyfin
    url: https://jellyfin.lan
    icon: jellyfin              # simple-icons / selfh.st slug, URL, or initials
    group: media
    health: { type: http, url: https://jellyfin.lan/health, interval: 60s }

groups:
  - { id: media, name: Media, color: "#8b5cf6" }

dashboards:
  - id: home
    name: Home
    default: true
    accent: "#22d3ee"
    widgets:
      - { id: apps-1, type: apps, title: Media, config: { groups: [media] } }

See config.example.yaml in the repo for the complete schema, including the global topBar and per-dashboard backgrounds.

Monitoring

Health checks & monitors

Each service can carry a health block. axboard runs one checker per app and shows a coloured status dot on its card. Five check types:

httptcppingdnspush
  • http — GET a URL and compare against expect_status.
  • tcp — dial host:port.
  • ping — ICMP (needs NET_RAW).
  • dns — resolve a host; optional body_contains match on the answers.
  • push — a passive heartbeat monitor: your job pings /api/push/<id> on a schedule and axboard marks the service down if a beat is missed.

Each check polls on its own health.interval. Set a fleet-wide default with server.default_interval — applied to any check that omits its own; it falls back to 60s when unset. Retries tolerate N failed checks before "down" so a blip doesn't false-alarm.

axboard keeps rolling uptime on disk and shows 24h / 7d / 30d windows in the service detail popover and on status pages. Mark a service critical: true so its outage counts as a major incident (see Status pages).

Monitoring

Alerts

axboard notifies you when a health-checked app goes down or recovers. Configure it entirely from the UI — ⋯ menu → Configure → Alerts — with a per-channel Save & test button, or hand-edit the alerts block. Every configured channel fires (all best-effort):

ChannelNeeds
ntfyA topic on ntfy.sh or your self-hosted ntfy — zero infra.
TelegramA bot token (from @BotFather) + your chat id.
EmailYour SMTP relay (host + credentials).
WebhookA plain JSON POST for Discord / Slack / custom.

A resend interval re-notifies while a service stays down; you can mute noisy services or pause all alerts for a maintenance window. Certificate expiry is checked on every HTTPS service and alerts before it lapses.

Monitoring

Status pages

Server-rendered status pages that need no JS — the default at /status and any number of named pages at /status/<slug>. Each groups the chosen services with a status dot, a history strip, 24h/7d/30d uptime, response time and cert-expiry warnings, plus an embeddable SVG badge at /status/badge/<id>.

Build them from ⋯ menu → Configure → Status pages with a live preview. Per page:

  • Identity — title (with its own colour), slug, header/footer text, hide the "Powered by axboard" line.
  • Summary banner — a plain-language headline in one of five styles: tint · minimal · strip · outline · solid.
  • Appearance — dark/light theme, width, and a backdrop (colour / gradient / image with blur & dim).
  • Content — include whole groups and/or pick individual services.
  • Notices — manual banners for incidents and scheduled work.

Severity by criticality

The banner colour means something. A critical service down turns it red; non-critical outages go amber and escalate to red once a configurable number are down at once (the "red at N" threshold).

all operational degraded / partial critical disruption
i
When authentication is on, status pages are gated behind a login by default. Tick Public (no login) on a page (public: true) to share it while the dashboard stays private. With auth off, all pages are public.

Operating

Authentication

axboard is open by default — LAN-bound, no login, meant to sit behind a reverse proxy. There is an optional, opt-in built-in login for when a proxy isn't in the picture. It stays off until you add a user.

1 · Generate a password hash

# argon2id — interactive (no echo) or piped
podman exec -it axboard /usr/local/bin/axboard passwd axel
echo -n 'your-password' | ./axboard passwd axel

2 · Paste the snippet into config.yaml

server:
  bind: 0.0.0.0:8080
  auth:
    session_ttl: 168h        # optional, default 7d
    users:
      - username: axel
        password_hash: "$argon2id$v=19$m=65536,t=3,p=4$…"

With one or more users, the SPA shows a login screen and the whole /api surface requires a signed-cookie session — except heartbeat ingest (/api/push/*), /healthz and /metrics, which stay open for external jobs. Log out from the ⋯ menu.

Hashes are never sent to the browser and can't be edited through the structured UI save path — manage users by editing config.yaml plus axboard passwd. The session-signing secret is auto-generated into session.key beside state.yaml; deleting it logs everyone out.

i
Built-in login is a lightweight fallback, not an IdP. For WAN exposure, prefer a reverse proxy with forward-auth (Authentik, Authelia, oauth2-proxy). Either way, bind server.bind to a LAN address.

Operating

Deployment

axboard ships as a single multi-arch (amd64 / arm64) image. There's nothing to build — pull the image, drop in a compose file, create your config.yaml, and bring it up. Tags: latest and pinned versions like v0.2.0.

1 · Bare minimum

Everything you actually need to run: the image, a port, and two volumes. Bridged networking — the CPU / memory / disk widgets still work; only real host network I/O and Wake-on-LAN need the host-access grants shown next.

services:
  axboard:
    image: axboard/axboard:latest
    container_name: axboard
    restart: unless-stopped
    ports:
      - "8080:8080"
    volumes:
      - ./config:/etc/axboard:Z       # your config.yaml (bind the directory)
      - axboard-state:/var/lib/axboard:Z

volumes:
  axboard-state:

2 · Full (all host access)

The same service with every optional grant, each labelled with the widget it unlocks. Remove any you don't want.

services:
  axboard:
    image: axboard/axboard:latest      # pin a version in prod, e.g. :v0.2.0
    container_name: axboard
    restart: unless-stopped

    # --- networking -------------------------------------------------------
    # Host networking lets the Host stats / Resource gauge / Network graph
    # widgets read REAL host network I/O, and lets Wake-on-LAN reach the LAN
    # broadcast. With it, the app binds the host port directly (no ports:).
    network_mode: host
    # Prefer bridged instead? Drop network_mode above and map the port —
    # CPU/RAM/disk still report the host, but network I/O shows only the
    # container's own traffic:
    # ports:
    #   - "8080:8080"

    # --- optional host access (remove any you don't want) -----------------
    pid: host                        # Top processes widget sees host processes
    cap_add:
      - NET_RAW                       # ICMP "ping" health-check type
    security_opt:
      - label=disable                 # SELinux: reach the container socket (discovery)

    volumes:
      # Required: your config dir (bind the DIRECTORY, not the file, so hot
      # reload sees create/rename events) + a named volume for machine state.
      - ./config:/etc/axboard:Z
      - axboard-state:/var/lib/axboard:Z
      # Optional: read-only container socket → auto-discover services from
      # running containers. (Docker: /var/run/docker.sock)
      - ${XDG_RUNTIME_DIR:-/run/user/1000}/podman/podman.sock:/var/run/docker.sock:ro
      # Optional: read-only host root → Filesystems widget statfs's real mounts.
      - /:/host:ro,rslave

    environment:
      - AXBOARD_HOST_ROOT=/host        # pair with the /host bind above

    healthcheck:
      test: ["CMD-SHELL", "wget -q -O- http://127.0.0.1:8080/healthz || exit 1"]
      interval: 30s
      timeout: 3s
      retries: 3

volumes:
  axboard-state:
i
Minimal setup? Keep only image, the two volumes, and a port mapping. Add each grant above only when you want the widget it unlocks — none are needed to run.

3 · Your config

mkdir -p config
curl -o config/config.yaml https://…/config.example.yaml   # or write your own
docker compose up -d

Open http://<host>:8080 and edit config/config.yaml — the server hot-reloads on save. State (layouts, uptime history, uploaded icons, the auth session key) lives in the axboard-state volume.

Updating

docker compose pull && docker compose up -d
!
Exposure. axboard is open by default — bind it to a LAN address. Anyone who can reach the port can read and edit the config unless you enable the built-in login or put a forward-auth proxy (Authentik / Authelia / oauth2-proxy) in front.
